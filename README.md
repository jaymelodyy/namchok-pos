**ยังไม่ได้ตรวจ (ผมทำไม่ได้ใน sandbox — ต้องมีคนลองจริง):**

- มือถือจริง (iPhone Safari, Android Chrome), กล้องถ่ายรูปจริง (`capture=environment`), รูป HEIC จาก iPhone, ขนาดปุ่มกดเทียบนิ้วจริง
- PWA: Add to Home Screen และ service worker บน production build จริง
- พิมพ์ใบเสร็จ/ใบรับประกันออกเครื่องพิมพ์จริง (มีแค่ CSS print)
- โหลดหลายผู้ใช้พร้อมกันผ่าน API จริง / เครือข่ายมือถือที่หลุดบ่อย (ทดสอบได้แค่การตัด WebSocket ด้วย Playwright)

## 2. ติดตั้งกับ Supabase จริง

> **ติดตั้งบนโปรเจกต์ของ Jay แล้ว (ขั้น 1–4 ด้านล่าง ทำเสร็จ — ดู 1.1)** ; หัวข้อนี้ไว้สำหรับติดตั้งซ้ำ/โปรเจกต์ใหม่ ; ขั้นที่ยังต้องทำเองคือขั้น 5 (ตั้งค่าแอปให้ชี้โปรเจกต์ และนำขึ้น host แบบ HTTPS) และขั้น 7

ต้องมี: โปรเจกต์ Supabase (Postgres 15 ขึ้นไป — migration ใช้ `nulls not distinct`), Node 20+

1. **สร้างโปรเจกต์ Supabase** แล้วเปิด SQL Editor
2. **รัน migration ตามลำดับ ทีละไฟล์** (หยุดดู error ทุกไฟล์):
   `0001_schema` → `0002_rls` → `0003_rpc` → `0004_storage` → `0005_hide_money_from_non_finance` → `0006_phase2_amendments` → `0007_assignments_requisitions` → `0008_qc_labor` → `0009_realtime` → `0010_multi_technician_assignment` → `0011_owner_crew_control` → `0012_unlimited_crew` → `0013_daily_wages` (ทั้งหมดอยู่ใน `supabase/migrations/`)
   - **0006–0009 เป็นของเฟส 2** ; ถ้าเคยรัน 0001–0005 ไปแล้วบนโปรเจกต์จริง รันต่อจาก 0006 ได้เลย (0006 แก้กติกา VAT/ใบรับประกัน และเพิ่มตารางคืนเงิน)
   - **0009 ผูกตารางกับ publication `supabase_realtime`** (Supabase มีให้อยู่แล้ว) — ถ้าเป็น Postgres ธรรมดาที่ไม่มี publication นี้ จะข้ามไปโดยไม่ error
   - ถ้าโปรเจกต์มี migration ถึง `0012` แล้ว ให้รัน `0013_daily_wages.sql` เพียงไฟล์เดียว
3. **รัน seed:** `supabase/seed.sql` (สร้างสาขา NTW, หมวดหมู่, แคตตาล็อก, แบบฟอร์มเช็คสภาพ และเรตงานเพิ่มเริ่มต้น — รันซ้ำได้โดยไม่เขียนทับเรตที่แก้แล้ว)
4. **สร้างผู้ใช้** ที่ Authentication → Users (อีเมล + รหัสผ่าน) ให้ครบ owner / admin / ช่าง (ได้หลายคน) / คลัง แล้วผูกกับตาราง `users` ใน SQL Editor:
   ```sql
   insert into users(id, branch_id, full_name, role)
   select '<auth uid ของผู้ใช้>', id, 'ชื่อที่แสดง', 'owner'   -- owner | admin | technician | warehouse
   from branches where code = 'NTW';
   ```
   (ผู้ใช้ที่ไม่มีแถวใน `users` ไม่มีบทบาท จึงไม่ควรเห็นข้อมูล — แต่ผมยังไม่ได้เขียนเทสต์กรณีนี้โดยตรง) ควรปิดการสมัครเองในตั้งค่า Authentication ของ Supabase เพื่อไม่ให้คนนอกสร้างบัญชีได้ ; **ชื่อที่แสดง (`full_name`) ของช่างจะขึ้นบนบอร์ดและในหน้าค่าแรง**
5. **ตั้งค่าแอป:** คัดลอก `.env.example` เป็น `.env.local` แล้วใส่ `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` และ `SUPABASE_SERVICE_ROLE_KEY` — service-role key ใช้เฉพาะ API ฝั่งเซิร์ฟเวอร์จัดการบัญชีพนักงานเท่านั้น **ห้ามใส่ prefix `NEXT_PUBLIC_`, ห้ามส่งให้ client และห้าม commit**
6. `npm install` → `npm run dev` (หรือ `npm run build && npm start`) เปิดบนมือถือแล้วเข้าสู่ระบบด้วย owner
7. **เจ้าของกรอกข้อมูลจริง:** หน้า "แคตตาล็อก" ใส่ **ราคา** และ **ระยะประกัน** ทุกรายการ และสำหรับรายการบริการที่ต้องจ่ายค่าแรงช่าง ใส่ **ค่าแรงช่าง (`labor_rate`)** กับ **จำนวนช่างที่ต้องใช้ (`crew_size`)** — รายการที่ `labor_rate` ว่าง/0 จะไม่เกิดค่าแรง ; หน้า "ตั้งค่า" ใส่ชื่อร้าน ที่อยู่ เลขผู้เสียภาษี ท้ายใบเสร็จ เพดานส่วนลด VAT (**ราคาทั้งหมดถือว่ารวม VAT แล้ว**)

**seed ตั้งใจให้ราคาทุกแถว = 0 และ `warranty_months` ว่างทั้งหมด** (จากสเปก: ห้ามเดา) ใบงานที่ยังมีบรรทัดราคา 0 โดยไม่ใส่เหตุผลจะอนุมัติใบเสนอราคาไม่ได้

## 3. รันทดสอบบนเครื่อง

### 3.1 ทดสอบฐานข้อมูล (ต้องมี Postgres 15+ ที่เป็น superuser ในเครื่อง)
```bash
export PGHOST=127.0.0.1 PGPORT=5432 PGUSER=postgres PGPASSWORD=...   # ปรับตามเครื่อง
npm install
npm run test:db      # สร้างฐาน namchok_test ใหม่ทุกครั้ง (drop ของเดิม) — อย่าชี้ไปฐานที่มีข้อมูลจริง
```
ผลที่ได้ตอนส่งงาน: `==== สรุป: ผ่าน 110 / 110 ====`

### 3.2 ทดสอบหน้าจอ (เดโมในเครื่อง — ข้อมูลสมมติเท่านั้น)
`tools/dev-api` เป็นตัวจำลอง Supabase API (รวม Realtime จำลอง) ที่ต่อ Postgres จริง **รหัสผ่านทุกบัญชี `demo1234` และ JWT secret ฝังในโค้ด ห้ามใช้กับข้อมูลจริงหรือเปิดสู่อินเทอร์เน็ต**
```bash
export PGHOST=127.0.0.1 PGPORT=54329 PGUSER=postgres
bash tools/e2e/reset-demo.sh                     # สร้างฐาน namchok_demo ใหม่ + seed + เริ่ม dev-api ที่พอร์ต 54330 (ปฏิเสธฐานที่ไม่ลงท้าย _demo)
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54330 NEXT_PUBLIC_SUPABASE_ANON_KEY=dev-anon-key npx next dev -p 3100 &
bash tools/e2e/run-p2.sh                         # ชุดเฟส 2 (รีเซ็ตฐานเดโมให้เอง) ต้องมี Chromium (ตั้ง CHROME_PATH ถ้าไม่ใช่ตำแหน่งเดิม)
bash tools/e2e/run-all.sh                        # ชุดเฟส 1 (ต้องรัน reset-demo.sh ก่อนทุกครั้ง)
```
- ถ้าเครื่องยังไม่มี Postgres รันอยู่ ให้เริ่มชั่วคราวได้ เช่น `pg_ctl -D /tmp/pgdata -o "-p 54329 -c listen_addresses=127.0.0.1" -l /tmp/pg.log start` (ต้องสร้าง data dir ด้วย `initdb` ก่อน — ถ้าเป็น root ให้รันผ่านผู้ใช้ `postgres`)
- บัญชีเดโม: `owner@` · `admin@` · `tech@` (ช่างหนึ่ง) · `tech2@` (ช่างสอง) · `stock@` (คลัง) + `demo.local` (รหัส `demo1234`)
- สคริปต์ e2e ต้องรันบนฐานเดโมที่เพิ่งสร้างใหม่ (ค่าที่ตรวจ เช่น ยอด/ทะเบียนรถ อิงข้อมูลเริ่มต้น `seed-demo.mjs`) ถ้ารันซ้ำบนฐานเดิมผลอาจเพี้ยน — ให้ `reset-demo.sh` ทุกรอบ ; ภาพหน้าจอเก็บใน `shots/`
- ตรวจ Realtime จำลองด้วย supabase-js ตัวเดียวกับแอป (ไม่ใช้เบราว์เซอร์) : `node tools/e2e/realtime-probe.mjs` — **สคริปต์นี้เปลี่ยนข้อมูลในฐานเดโม (เลื่อนคำขอเบิก/รับงาน) ห้ามรันขณะ `run-p2.sh`/`run-all.sh` กำลังทำงาน และต้อง `reset-demo.sh` ก่อนรันชุดทดสอบอื่นต่อ** (ผมเคยรันทับกันโดยพลาดครั้งหนึ่ง ทำให้ p2-visibility ล้มเพราะข้อมูลตั้งต้นเปลี่ยน — จึงรันชุดเฟส 2 ใหม่ทั้งชุดตามที่รายงานด้านล่าง)

หมายเหตุความซื่อสัตย์ของรอบนี้: รอบแรกของชุดนี้ `p2-visibility` ล้ม 1 ข้อ เพราะผมรัน `realtime-probe` ทับขณะชุดทดสอบกำลังทำงาน (ข้อมูลตั้งต้นเปลี่ยน — ไม่ใช่บั๊กของแอป) ; รีเซ็ตฐานแล้วรันใหม่ทั้งชุดจึงได้ผลด้านบน

## 5. ผังการทำงานแต่ละบทบาท (เฟส 2)

- **owner / admin** — หน้า "ใบงาน" มุมมอง **บอร์ด** (คอลัมน์ตามสถานะ + แถบช่าง ว่าง/รับงานแล้ว/กำลังทำ) หรือ **รายการ** ; อนุมัติใบเสนอราคา → ระบบสร้างคำขอเบิกอัตโนมัติ ; มอบหมาย/เอาช่างออก (เอาออกต้องมีเหตุผล) ; กรอกผล QC ; รับมัดจำ/รับชำระ/คืนเงิน ; ปิดงานพร้อมระบุวันส่งมอบ ; owner เห็นหน้า "ค่าแรง" ของทุกคนและติ๊กจ่าย
- **ช่าง** — หน้า "งานของฉัน" : กลุ่มงานของตัวเอง + กลุ่ม "งานว่าง" พร้อมปุ่ม **รับงาน** ; เห็นรายการงาน/อะไหล่ **ไม่มีราคา** ; เริ่มงาน/ส่งตรวจ QC ; ถ้า QC ไม่ผ่านมีแถบแดงพร้อมเหตุผลในหน้าใบงาน ; หน้า "ค่าแรง" เห็นเฉพาะของตัวเอง เลือกช่วงวันที่ ได้ (วันนี้/7 วัน/เดือนนี้/เดือนก่อน/กำหนดเอง) พร้อมยอดรวม/จ่ายแล้ว/ค้างจ่าย
- **คลัง** — หน้า "เบิกอะไหล่" : เห็นเฉพาะคำขอ (เลขใบงาน ทะเบียน รายการ จำนวน) กด จัดเตรียมแล้ว → ส่งมอบแล้ว ; ไม่เห็นลูกค้า ไม่เห็นเงิน

ภาพหน้าจอตัวอย่าง (ข้อมูลสมมติ) อยู่ใน `docs/screens/`

## 7. ข้อจำกัดที่ทราบ (รายละเอียดใน DECISIONS.md / TODO.md)

- ยังไม่มี **ช่องซ่อม (bay)** ; ช่างรับ **หลายงานพร้อมกันได้** ; การ์ดใน "งานของฉัน" ไม่มีป้ายบอก "QC ไม่ผ่าน" (แถบเตือนอยู่ในหน้าใบงานเท่านั้น)
- ค่าแรงเกิดตอนปิดงานเฉพาะช่างที่รับงานอยู่ตอนนั้น (ไม่มีช่างรับ = ไม่เกิดค่าแรง ; ช่างที่ถูกเอาออกก่อนปิดไม่ได้) ; "จ่ายแล้ว" เป็นการติ๊กรายรายการ ยังไม่มีบันทึกรอบจ่าย
- ไม่รองรับลากวางการ์ดบนบอร์ด (ตั้งใจ — เปลี่ยนสถานะผ่านปุ่มในใบงานเพื่อให้กติกาตรวจครบ)
- ป้ายแจ้งเตือน (toast) ทับขอบบนของหัวหน้าจอเล็กน้อยบนมือถือ
- admin อ่าน `cost` (ต้นทุน) ผ่าน API ได้ · ช่าง/คลังอ่าน `labor_rate`/`crew_size` ได้ — **Jay ตัดสินแล้วว่าไม่ต้องปิด** · `job_discount_blocked` ไม่ตรวจสาขา (คืนแค่ true/false) ยังไม่ได้แก้
- ไม่รองรับออฟไลน์ (ตั้งใจ: service worker แคชเฉพาะไฟล์ static ไม่แคชข้อมูลเงิน/ลูกค้า) — เมื่อออฟไลน์ ไฟสถานะที่หัวหน้าจอเปลี่ยนเป็น "ออฟไลน์" และกลับมาโหลดใหม่เองเมื่อต่อได้
- เพิ่มผู้ใช้ผ่าน Supabase Dashboard (ยังไม่มีหน้าจัดการผู้ใช้ในแอป)

**ไม่ได้ทำ (เป็นของเฟส 3 ตามสเปก):** Dashboard, แจ้งเตือน LINE, ติดตามลูกค้า/ประกัน, รายงานเพิ่มเติม
